# 今天吃啥（home-pantry）需求分析报告

- 文档版本：1.0
- 项目阶段：第一期 MVP
- 产品形态：微信小程序
- 产品名称：今天吃啥
- 工程名称：home-pantry
- 文档状态：第一期开发基线

---

## 1. 项目概述

### 1.1 项目描述

「今天吃啥」是一款面向个人和家庭的智能食材库存与菜谱推荐小程序。用户维护家中现有食材及数量，管理菜谱、必选配料、可选配料和制作步骤；系统根据实际库存、菜品难度和近期制作记录，生成有明确食材匹配结果的每日菜品推荐。

产品不以“海量菜谱浏览”为核心，而以“当前库存能做什么”为决策入口，帮助用户减少每天思考吃什么的时间，提升现有食材利用率，减少重复做菜和食材浪费。

### 1.2 项目目标

1. 快速记录家庭食材库存：只填名称与分类，不要求维护数量单位。
2. 建立结构化菜谱库，区分必选与可选配料。
3. 根据库存计算真实可制作程度，并把库存齐全的菜品优先展示。
4. 根据最近制作记录和难度偏好调节推荐排序。
5. 每日生成并保存推荐结果，首页可查看摘要和明细。
6. 建立家庭维度的数据结构，为后续多人协同做好准备。

### 1.3 目标用户

- 想快速决定每天做什么菜的个人用户。
- 需要共同管理食材和菜谱的家庭用户（家庭协同安排在后续阶段）。
- 希望优先消耗已有食材、减少浪费的用户。

### 1.4 核心业务闭环

```text
微信进入小程序
    ↓
进入默认家庭空间（或用邀请码加入他人家庭）
    ↓
录入食材库存（名称、分类）
    ↓
浏览菜谱（必选配料、可选配料、难度、步骤；由服务端维护）
    ↓
推荐引擎按“有该食材即满足”匹配库存
    ↓
按“可制作优先”生成每日推荐
    ↓
查看推荐详情（已有、缺少、制作步骤）
    ↓
标记已制作，写入家庭做菜记录
```

## 2. 功能范围与页面结构

### 2.1 全局导航

底部固定两个 Tab，首页内部再按分区切换：

- **首页**：左侧竖向分区栏切换 今日推荐 / 食材库存 / 菜品食谱 / 今日宜吃。
- **我的**：用户资料、家庭空间（成员管理）、做菜记录、推荐与通知、退出登录。

首页主内容区仍为手机竖屏纵向布局，左侧分区栏固定宽度，保证微信小程序在常见手机尺寸上的可用性。

### 2.2 首页

#### A. 食材库存

- 新增、删除、编辑食材（仅名称与分类）。
- 食材以**正方形磁贴、一行三个**展示，图标按分类统一（蔬菜🥬/肉类🥩/水产🐟/蛋奶🥚/主食🍚/调味品🧂/其他🧺）。
- 食材按类别分组；提供“全部/蔬菜/肉类/水产/蛋奶/主食/调味品/其他”等筛选，列表始终按分类顺序排列。
- 提供「刷新」入口，主动拉取家庭成员最新维护的库存与推荐。
- 食材字段：名称、类别（数量与单位仅作为数据字段保留，MVP 界面不维护，也不参与推荐判定）。
- 推荐只判断“库存里有没有这种食材”，是否够用由用户现场判断，避免逐项填写数量带来的操作负担。
- 后续扩展：精确库存（数量/单位换算）、保质期、临期提醒、采购来源、库存变动记录。

#### B. 菜品食谱

- 两列卡片展示，卡片显示插画、序号、难度、菜名、制作时长与配料数。
- **前端只读**：不提供新增/删除入口；菜谱由服务端接口或数据脚本维护（`POST /api/recipes` 保留）。
- 点击卡片查看详情，详情区分必选配料、可选配料和制作步骤。
- 菜谱字段：名称、图片/emoji 插画、描述、难度等级、准备时间、烹饪时间、配料和步骤。
- 难度等级：1 入门、2 简单、3 进阶、4 挑战。

#### C. 今日宜吃

- 每天生成推荐批次，首页按推荐顺序逐条显示摘要。
- 摘要显示菜品名称、难度、库存匹配状态、已拥有配料数量、缺少的必选配料。
- 点击摘要查看推荐明细：推荐理由、必选配料匹配、缺少的必选配料、缺少的可选配料、制作步骤。
- 全部必选配料齐全的菜品必须排在缺少必选配料的菜品前面。
- 支持“已制作”反馈，记录写入家庭做菜记录并参与近期重复惩罚；“暂不想吃”不在本期范围。

### 2.3 我的

#### 用户资料

- 微信用户身份与基础资料。
- 用户昵称自定义。
- 预设头像选择，不开放用户上传，避免第一期引入文件存储、图片审核和额外流量成本。
- 退出登录。

#### 家庭

- 数据模型从第一期开始采用 household 归属。
- 第一期已实现基础家庭协同：管理员生成邀请码（24 小时有效）、成员通过邀请码加入、成员列表、管理员移除成员、多家庭切换；成员可查看并使用家庭的库存、今日宜吃与最合适的一餐，但不能邀请或移除他人。
- 新用户通过分享卡片进入时，登录接口会带上邀请码：校验有效则**直接加入邀请方家庭，不再创建空家庭**。
- 退出登录采用服务端令牌版本机制（`User.tokenVersion`）：调用 `POST /auth/logout` 后旧 JWT 立即失效。
- 二期再补充：更细的权限（如是否允许成员维护菜谱）、操作同步与冲突处理、分享卡片邀请。

#### 做菜记录

- 位于「家庭空间」与「推荐与通知」之间，以表格展示：序号、做菜人、菜品、时间。
- 记录按家庭共享，成员与管理员都能看到全部家庭成员的制作记录。
- 数据来源为「已制作，记一笔」写入的 `meal_history`。

#### 设置（推荐与通知）

- 每日推荐开关：开启后按设定时间由服务端生成当日推荐批次，关闭后不自动生成。
- 推荐时间：HH:mm 选择；关闭开关时该选择禁用（不生效）。
- 微信订阅消息：当前只落库偏好，实际发送依赖已审核模板与用户授权，尚未接入。

### 2.4 MVP 不包含

- 多人实时协同与操作冲突处理（家庭邀请、角色权限已实现基础版）。
- 食材拍照识别、OCR、条码识别。
- 自动生成复杂菜谱及营养学建议。
- 购物平台、外卖平台或电商下单。
- 一周饮食计划、营养分析和语音烹饪助手。
- 真实生产级微信登录与每日无条件推送承诺（需真实 AppID、Secret、模板资质及用户授权）。

## 3. 推荐技术栈

### 3.1 小程序前端

| 层级 | 选型 | 说明 |
|---|---|---|
| 小程序框架 | Taro 4.3.3 | React 开发体验，编译微信小程序 |
| UI 框架 | React 18 + TypeScript | 组件化与类型约束 |
| 组件实现 | Taro 原生组件 + 项目自定义组件 | 确保运行于小程序环境 |
| 视觉体系 | shadcn/ui 风格 Token | 借鉴卡片、弹层、圆角、间距、边框和状态色，不直接搬运 Web 组件 |
| 样式 | Sass / SCSS | 变量、主题和模块样式 |
| 状态 | React hooks；复杂后续可引入 Zustand | 目前 MVP 状态边界较小 |
| 本地持久化 | Taro Storage | 本地演示与离线缓存 |

说明：shadcn/ui 的现成组件是面向 Web React DOM 的实现，不能把 Dialog、Select 等 Web 组件直接当作原生微信小程序组件使用。本项目在小程序内实现轻量 Modal、Card、Button、Tag、Form 等组件，并复用 shadcn 风格设计规范。

### 3.2 后端

| 层级 | 选型 | 说明 |
|---|---|---|
| 框架 | NestJS 12 | 模块化、依赖注入、守卫和任务调度 |
| 语言 | TypeScript | 与前端统一语言 |
| ORM | Prisma 7 | 类型安全的数据访问和迁移 |
| 主数据库 | SQLite（`@prisma/adapter-better-sqlite3`） | 单文件零运维，适合前期低并发；数据文件 `apps/api/prisma/dev.db`。人数增多后可平滑迁移到 PostgreSQL（换 provider + adapter，业务代码不变） |
| 缓存/队列基础设施 | Redis 7（按需启用） | 缓存、任务去重及后续 BullMQ |
| 定时任务 | @nestjs/schedule | 每日生成推荐批次 |
| API | RESTful JSON | 小程序调用 |
| 认证 | 微信 code2session + 服务端会话/JWT（上线前完成） | 不信任客户端传入的用户 ID |

### 3.3 推荐系统

采用“规则算法负责事实、AI 负责语言生成”的分层方式。

- 匹配口径：库存中存在同名食材即视为满足，不比较数量与单位（MVP）。
- 第一优先：库存匹配等级（必选配料全部满足 > 缺少少量 > 缺少较多）。
- 同等级内：综合必选配料覆盖率、难度适配、近期重复惩罚、可选配料匹配度。
- 推荐详情中的已有/缺少配料必须由数据库查询结果确定。
- AI 不得自行补造库存数量或判断库存充足；AI 接口不可用时仍可通过规则引擎输出推荐。

建议起始权重（可通过后续反馈调参）：

| 因素 | 参考权重 |
|---|---:|
| 必选配料覆盖率 | 50% |
| 最近制作难度适配度 | 20% |
| 近期重复惩罚 | 20% |
| 可选配料匹配度 | 10% |

以上分数仅用于同一库存匹配等级的组内排序，不能打破“必选配料齐全优先”的硬规则。

## 4. 数据库设计

### 4.1 数据库选型

当前采用 **SQLite** 单文件数据库（`apps/api/prisma/dev.db`），通过 Prisma 驱动适配器 `@prisma/adapter-better-sqlite3` 访问：零安装、零运维、备份即复制文件，适合前期低并发与本地开发。

核心数据仍保持关系型建模：家庭与成员、家庭与库存、菜谱与食材、推荐批次与推荐条目依赖关系约束与唯一索引。待用户量增长（并发写入成为瓶颈）时，切换为 PostgreSQL 只需替换 `datasource provider` 与适配器，业务代码与 schema 结构基本不变；Redis 仍作为后续缓存/异步任务组件按需启用。

### 4.2 核心表

| 表 | 职责 | 关键字段 |
|---|---|---|
| users | 用户身份与资料 | id、openid、unionid、nickname、avatar_key、status |
| households | 家庭空间 | id、name、created_by、timezone |
| household_members | 家庭成员关系 | household_id、user_id、role、joined_at |
| household_invites | 家庭邀请码 | id、code（唯一）、household_id、created_by、expires_at |
| ingredient_categories | 食材分类 | id、name、sort_order |
| ingredients | 食材基础档案 | id、name、category_id、default_unit |
| inventory_items | 家庭库存 | household_id、ingredient_id、quantity、unit |
| recipes | 菜谱 | id、household_id、name、difficulty、prep_minutes、cook_minutes |
| recipe_ingredients | 菜谱配料关系 | recipe_id、ingredient_id、kind、amount、unit、sort_order |
| recipe_steps | 菜谱步骤 | recipe_id、step_no、instruction |
| meal_history | 制作历史 | household_id、user_id、recipe_id、cooked_at |
| recommendation_batches | 推荐批次 | household_id、recommendation_date、algorithm_version、generated_at |
| recommendation_items | 推荐结果 | batch_id、recipe_id、rank、match_level、match_snapshot |
| notification_settings | 通知偏好 | household_id、enabled、mode、preferred_time |
| notification_logs | 通知日志 | user_id、batch_id、template_id、status、sent_at |

### 4.3 关键建模规则

1. `ingredients` 是基础食材档案，`inventory_items` 是家庭实际库存，两者不得混为一张表。
2. `recipe_ingredients.kind` 取 `REQUIRED` 或 `OPTIONAL`。
3. MVP 推荐不比较数量与单位（有即算有）；后续开启精确库存时，数量比较必须在同一量纲内进行，且需要统一的单位换算服务。
4. 库存和菜谱都必须有家庭归属或明确的系统共享归属策略。
5. 推荐结果要持久化，保存算法版本和配料匹配快照，便于回看和解释。
6. 生产环境涉及库存扣减时使用事务并校验并发更新，避免多成员同时制作导致库存负数。

| 用户资料 | 昵称、emoji 头像、角色徽标、退出登录/游客模式 | 已完成 |
| 库存 | 新增/编辑（名称+分类）、删除、分类筛选、手动刷新 | 已完成 |

| 今日宜吃 | 推荐列表、详情、标记已制作（写入做菜记录） | 已完成 |

| 服务端 | NestJS 模块、SQLite schema、库存/菜谱/推荐/历史/通知/家庭 API | 已完成 |
| 文档 | 需求、交互、开发指南、依赖说明 | 已完成 |

验收标准：

- 新用户可看到示例食材和菜谱，其他人加入后能看到同一份数据。
- 可新增/编辑/删除食材，按分类顺序展示，可手动刷新。
- 菜谱详情能区分必选/可选配料与步骤（只读）。
- 必选配料齐全的菜品排在缺料菜品前面，判定只看“有没有”。
- 推荐详情正确列出已有、缺少必选、缺少可选配料。
- 标记已制作写入做菜记录，并影响近期推荐排序。
- 首页与我的可切换，资料改动、家庭切换、邀请码加入均持久化。

### 二期：家庭协同与库存增强

建议 2–3 周，依赖家庭数据模型已经建立。

- 创建家庭、邀请成员、邀请码/分享卡片加入（邀请码邀请、分享卡片邀请、成员增删、多家庭切换已完成）。
- 家庭创建者和普通成员权限（管理员/成员的基础权限已完成）。
- 家庭成员共享库存和菜谱（共享库存与推荐已完成）。
- 操作同步与冲突处理（待做）。
- 做菜后按菜谱用量扣减库存。
- 库存变动流水、保质期和临期提醒。
- 缺少配料加入购物清单。

### 三期：AI 个性化

建议 3–4 周，重点提升推荐质量。

- 口味、辣度、荤素、忌口和过敏原偏好。
- 基于反馈的个性化排序。
- AI 推荐理由和烹饪建议。
- 自然语言生成菜谱。
- 周菜单、荤素搭配和菜品组合。
- 推荐效果统计及权重调优。

### 可拓展功能

- 冰箱照片识别食材、语音录入库存。
- 食材保质期和临期消耗提醒。
- 营养素/热量估算（需可靠食物成分数据源）。
- 智能采购、购物清单共享。
- 步骤式语音烹饪助手。
- H5/App、多家庭和社区菜谱。

## 6. 消息推送规则与限制

“后台每天自动生成推荐”与“微信每天主动发服务通知”是两件不同的事。

- 后台可以按家庭时区和偏好生成推荐数据。
- 小程序首页可以在用户下次进入时显示新推荐。
- 微信订阅消息需要用户授权及可用模板；一次性订阅通常一次授权对应一次发送。长期订阅资格、模板可用性和主体类目受到微信平台规则限制。
- 因此 MVP 交付自动推荐生成和消息授权/发送接口，不承诺对所有用户无条件每日推送。
- 上线前应使用真实小程序主体验证类目、模板、授权流程、发送频率及审核规则。

## 7. 非功能性要求

- **安全**：所有家庭数据按服务端身份与 household membership 校验，不能信任客户端 householdId。
- **可维护**：业务按 auth、inventory、recipes、recommendations、notifications 模块拆分。
- **可扩展**：推荐引擎使用独立纯函数/服务，AI Provider、微信消息 Provider 采用适配层。
- **性能**：首页一次性读取必要摘要；推荐结果按日持久化；对库存/菜谱查询建立索引。
- **可靠性**：AI 失败降级至规则算法；消息发送失败单独记录，不回滚推荐生成。
- **体验**：首屏优先显示今日推荐和库存概览，新增食材和查看推荐不超过少量步骤。

## 8. 交付边界与风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 微信订阅消息限制 | 无法承诺每天主动推送 | 先做自动生成和站内展示，接入授权消息 |
| 食材单位不统一 | 错误判定库存够用 | MVP 不比较数量与单位以规避该风险；开启精确库存时再引入单位字典和量纲换算 |
| 用户未维护库存 | 推荐相关性下降 | 新用户预置样例、简化录入、提醒维护 |
| 菜谱数据质量 | 推荐结果不准确 | 配料结构化、标准食材档案、逐步校验 |
| AI 输出不稳定 | 错误库存/步骤信息 | AI 不掌管事实匹配，规则引擎兜底 |

## 9. 本期完成定义

第一期完成的判断标准不是“有页面”，而是用户能够完成真实闭环：维护食材 → 维护菜谱 → 获取可解释推荐 → 标记制作。前端交付微信小程序可编译工程，后端交付可启动 API、数据库 schema、初始化数据与推荐算法，项目根目录提供开发和部署文档。
